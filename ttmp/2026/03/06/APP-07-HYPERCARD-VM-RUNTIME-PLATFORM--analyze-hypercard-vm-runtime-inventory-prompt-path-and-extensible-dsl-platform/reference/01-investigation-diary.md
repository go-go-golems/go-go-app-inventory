# Investigation diary

## Goal

Capture the exact investigation path used to trace how inventory chat generates runtime cards, how those cards are safely executed in QuickJS, and which extension seams are best suited for richer widgets, async HTTP work, and DB-query-backed runtime flows.

## Step 1: Trace The Existing End-To-End Hypercard Pipeline

The first step was to establish a file-backed trace from the user typing into the inventory chat window all the way to generated JavaScript running inside the frontend VM. Without that trace, any recommendation about "different UI DSLs" or "extra APIs" would have been speculative.

This step focused on the inventory backend, the chat transport, the runtime composer, the structured artifact extraction path, and the QuickJS host boundary. The goal was to determine where the system actually decides what the model should emit, and where the system actually decides what generated code is allowed to do.

### What I learned

- The system has two distinct extensibility planes:
  - inference-time prompt and middleware composition
  - runtime-time QuickJS execution and host dispatch
- The current hypercard prompt is already a DSL contract document. It describes both the UI helper API and the allowed state and dispatch surface.
- The current runtime is synchronous. Generated handlers emit intents immediately; they do not await host promises.
- The current system is more reusable than its naming suggests. It is already a generated runtime-card platform, not just an inventory hypercard feature.

### What was tricky to build

- The trickiest part of the trace was separating "what the model is told it can do" from "what the VM is actually allowed to do." The prompt makes the DSL look rich, but the real authority is the QuickJS bootstrap plus the host-side validator and dispatch router.
- Another sharp edge was request selection. The frontend code appears to support per-conversation profile selection, but the backend resolver uses a different parameter naming scheme and falls back to a cookie. That can easily mislead a reader into assuming runtime-pack selection is already conversation-scoped when it is not reliably so.

### What warrants a second pair of eyes

- Whether the unused `inventory_artifact_generator` middleware is intentionally left inactive or whether it was expected to enforce tag presence.
- Whether `defaultRegistrySlug` being defined but effectively unused in the current request resolver is intentional or an unfinished piece of profile-registry plumbing.
- Whether the immediate-dispatch plus queued-intent dual model is an intentional platform choice or just transitional overlap.

### What should be done in the future

- Align runtime selection transport fields before introducing conversation-scoped runtime packs.
- Introduce a generic runtime artifact envelope so future DSLs do not have to masquerade as `hypercard.card.v2`.
- Keep async side effects out of QuickJS itself and put them into effect hosts.

## Step 2: Compare Async Bridge Patterns And Derive The Platform Direction

This step shifted from pure tracing to design comparison. The question was no longer only "how does the current system work?" It became "which existing patterns should become the default future extension model?"

### Why

- I wanted the final recommendation to be grounded in patterns the repo already uses successfully.

### What worked

- SQLite provided the cleanest model for "generated card requests work, host runner executes work, result re-enters state, card rerenders."
- ARC provided the cleanest model for "request lifecycle lives in session state and pending domain intents are consumed by a dedicated effect host."
- The comparison made one major limitation obvious: the QuickJS runtime is synchronous, so promise-like in-VM fetch APIs are the wrong first extension point.
- The design doc naturally converged on a runtime-pack plus effect-bridge architecture rather than direct VM fetch.

### What didn't work

- One reducer search path was initially misleading because `apps/inventory/src/reducers.ts` only re-exports slices, so a narrow search there did not show the real action implementations. I corrected the search to look inside the feature slice files instead.


The actual implementations were in:

- `apps/inventory/src/features/inventory/inventorySlice.ts`

### What I learned

- The repository already has two extension styles:
  - direct Redux action handling
  - queued pending-intent consumption
- Both can work, but a new runtime extension should choose one pattern deliberately to avoid ambiguity.
- Richer widgets require changes in three places at once:
  - VM helper surface
  - output schema
  - React renderer
- Async HTTP and DB workflows belong in effect hosts or middleware, not in generated QuickJS code.

### What was tricky to build

- The trickiest design question was not the HTTP call itself. It was deciding where request lifecycle state should live. The ARC example mirrors status back into runtime session state while also keeping richer app snapshots in Redux. That is a useful pattern for future runtime-query bridges because it lets generated cards render from lightweight local session state while still benefiting from centralized host caching or snapshot stores.
- Another subtlety is that `dispatchRuntimeIntent(...)` immediately dispatches domain actions after also recording them in `pendingDomainIntents`. That makes the platform flexible, but it also means future bridge code has to be explicit about whether it consumes queued intents, immediate actions, or both.

### What warrants a second pair of eyes

- Whether the platform should keep supporting both immediate domain dispatch and queued pending-domain consumption in parallel.
- Whether future async bridges should standardize on session-state mirroring, domain-slice caches, or a hybrid model.
- Whether generated runtime artifacts should stay branded as "hypercards" or move to a more generic runtime-artifact vocabulary.

### What should be done in the future

- Add a runtime-pack registry on both backend and frontend.
- Introduce effect-host helpers for common async request lifecycle handling.
- Add one real inventory query bridge as the first production-grade proof of the new platform direction.
